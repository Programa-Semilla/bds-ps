# Feature Specification: Review & Funding-Agreement UX Refinements

**Feature Branch**: `027-review-funding-ux`
**Created**: 2026-05-26
**Status**: Draft
**Input**: Consolidated stakeholder review of the funding-agreement flow — eight UX/data refinements across the reviewer and applicant journeys.

## Overview

A stakeholder walkthrough of the funding-agreement flow surfaced eight refinements that share one purpose: make **submitted-item decision data legible and consistent at every touchpoint**, give reviewers the controls they expect, and make forms self-explanatory. This is a single consolidated feature delivered as eight independently testable user stories. No database schema changes are required by any story. Default culture is **es-CR**; all UI copy is localized (no English-only copy). The generated funding-agreement **PDF document body is explicitly unchanged** (spec 018 minimalism is preserved) — every data expansion in this feature is on-screen.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Generator shown by name, not GUID (Priority: P1)

When a reviewer or admin opens the funding-agreement page for an application, the "generated by" attribution currently shows a raw user GUID (e.g. `por 48120df3-9be7-4f93-920a-7b2934106ae8`), which is meaningless to a human reader. The attribution must show the generator's human-readable name.

**Why this priority**: Visible defect on a primary reviewer surface; trivial to fix; erodes trust in the page. The display-name resolution capability already exists in the system and is already used elsewhere on the same page (commission members).

**Independent Test**: Generate a funding agreement as a known user, open the funding-agreement page, and confirm the "Generado — … por X" line shows that user's full name (or email if name is unset), and never a GUID.

**Acceptance Scenarios**:

1. **Given** a funding agreement generated by a user who has a first and last name, **When** any reviewer/admin views the funding-agreement page, **Then** the attribution reads "… por {FirstName} {LastName}".
2. **Given** a generator whose name fields are empty but who has an email, **When** the page is viewed, **Then** the attribution falls back to the email address.
3. **Given** a generator whose account was later deleted, **When** the page is viewed, **Then** the attribution degrades gracefully (a stable fallback label) and never throws or shows a raw GUID to the user.

---

### User Story 2 - Confirm before executing or rejecting the signed convenio (Priority: P1)

On the signed-upload section of the funding-agreement page, "Aprobar" (which **executes** the agreement — a legally meaningful, hard-to-reverse action) and "Rechazar" currently commit immediately on click. Each must require an explicit confirmation step that states the consequence before it commits.

**Why this priority**: Executing or rejecting a signed agreement is consequential and not easily undone; an accidental click has real cost. The confirm-dialog infrastructure already exists in the codebase (spec 024) and is reused here.

**Independent Test**: As a reviewer, click "Aprobar" and then "Rechazar" on a signed upload; confirm that in each case a confirmation prompt appears stating the consequence, that dismissing it makes no change, and that confirming performs the action.

**Acceptance Scenarios**:

1. **Given** a signed upload awaiting reviewer action, **When** the reviewer clicks "Aprobar", **Then** a confirmation appears stating "Esto ejecuta el convenio." and the agreement is executed only after the reviewer confirms.
2. **Given** the same state, **When** the reviewer clicks "Rechazar", **Then** a confirmation appears stating "Esto rechaza la carga; el solicitante podrá enviar otra." and the rejection commits only after confirmation.
3. **Given** the reviewer dismisses either confirmation, **When** the dialog closes, **Then** no state change occurs and the reviewer remains on the page.
4. **Given** the reject path, **When** the reviewer confirms, **Then** the existing mandatory rejection comment is still required and enforced.

---

### User Story 3 - Richer applicant detail on the funding-agreement page (Priority: P2)

The funding-agreement page currently shows only the company name and the representative's name. A reviewer reviewing or executing an agreement needs fuller applicant context on the same screen.

**Why this priority**: Improves reviewer context and reduces navigation away from the page; depends on US5 for the reviewer-assigned code field. Screen-only — does not touch the PDF document.

**Independent Test**: Open the funding-agreement page for an application whose applicant has a legal ID, email, phone, group, and an assigned code; confirm all of those fields render on the page, and confirm the generated PDF document content is unchanged.

**Acceptance Scenarios**:

1. **Given** an application on the funding-agreement page, **When** a reviewer views it, **Then** the applicant block shows: company name, representative name, legal identification (value and type), email, phone, the reviewer-assigned applicant code, the applicant's group, and the submission date.
2. **Given** an applicant field that is empty (e.g. no phone), **When** the page renders, **Then** that field shows a neutral placeholder rather than blank or an error.
3. **Given** the page is viewed, **When** the funding-agreement PDF is generated, **Then** the PDF document body contains no additional applicant detail beyond what spec 018 already defines.

---

### User Story 4 - Consistent detailed decision summary across all five interaction screens (Priority: P1)

A reviewer and an applicant interact with the submitted items at five distinct stages. Today the level of detail differs at each stage — the reviewer's item-review screen is rich, but the applicant's decision screen omits technical specifications, the generate/sign/signed-review screens show approved lines only, and rejected lines lack supplier and amount context. The same detailed per-line decision summary must render at every stage.

**Why this priority**: This is the core of the feedback — the decision data must be "amplia" (ample) and identical in shape wherever the parties review it, so a reviewer or applicant sees the same complete picture when analyzing items, deciding, generating, signing, and reviewing the signed document. Required for legible, reportable decisions.

**Independent Test**: Drive one application through the full flow and, at each of the five screens, confirm the per-line summary shows the same fields (line code, product/type, category, technical specifications, approved supplier, amount with currency/CRC note, decision status) for both approved and rejected lines, with rejected lines additionally showing the reason and the quoted suppliers/amounts considered.

**The five stages**:
1. Reviewer item review (the first review screen).
2. Applicant accept/reject of the reviewer's per-item decisions.
3. Reviewer generate-agreement screen.
4. Applicant signing screen.
5. Reviewer review of the uploaded signed document.

**Acceptance Scenarios**:

1. **Given** an application with both approved and rejected lines, **When** the applicant opens the accept/reject screen, **Then** each line shows its technical specifications in addition to the fields already shown (status, selected supplier, amount, comment).
2. **Given** the same application, **When** the reviewer opens the generate-agreement screen, **Then** every line — approved and rejected — is listed with line code, product/type, category, technical specifications, supplier, amount, and decision status.
3. **Given** a rejected line, **When** it is shown on any of the five screens, **Then** it displays the rejection reason and the full set of suppliers quoted for that line with their amounts (since a rejected line has no single approved supplier).
4. **Given** the reviewer opens the signed-document review screen, **Then** the same detailed summary is present (not an approved-only subset).
5. **Given** a line whose quotation is in a non-CRC currency, **When** its amount is shown on any screen, **Then** the currency and the CRC conversion note are shown consistently with the existing multi-currency presentation.

### User Story 5 - Reviewer-assigned applicant code on the first review screen (Priority: P2)

Reviewers and admins need to assign their own identifier to each applicant (distinct from the applicant's self-entered legal ID). A code field already exists in the system but has no way to be set — it only displays read-only on the applicant's profile. Reviewers and admins must be able to assign and edit this code from the first review screen.

**Why this priority**: Closes an existing capability gap (the field is dangling — displayed but never writable). Enables internal reference-keeping. US3 depends on it for display.

**Independent Test**: As a reviewer, open the first review screen for an application, enter/edit the applicant code, save, and confirm it persists; then log in as that applicant and confirm the code appears read-only on the profile and cannot be edited there.

**Acceptance Scenarios**:

1. **Given** the first review screen, **When** a reviewer enters an applicant code and saves, **Then** the code is stored against the applicant and shown back on the review screen and on the funding-agreement page (US3).
2. **Given** an applicant who already has a code, **When** a reviewer edits it and saves, **Then** the new value replaces the old.
3. **Given** an applicant viewing their own profile, **When** they open the profile, **Then** the code is visible but read-only (no edit control).
4. **Given** the applicant has more than one application, **When** the code is set, **Then** it is associated with the applicant (per-user) and therefore consistent across that applicant's applications.
5. **Given** the code is not the legal ID, **When** it is assigned, **Then** it does not affect or validate against the applicant's legal identification.

### User Story 6 - Consistent required-field markers on every form (Priority: P2)

Required fields are marked inconsistently across the application — some forms show a red asterisk, others rely only on browser-level required behavior. Every required field on every form (applicant, admin, and reviewer) must carry a consistent visual marker distinguishing it from optional fields.

**Why this priority**: Improves usability and reduces submission errors app-wide; low risk; foundational consistency that other forms benefit from.

**Independent Test**: Visit each form in the app and confirm every required field carries the same marker (and the same accessible label), while optional fields carry none.

**Acceptance Scenarios**:

1. **Given** any form with required and optional fields, **When** it renders, **Then** each required field shows the standard marker (a red asterisk with an accessible label such as "campo obligatorio") and optional fields show no marker.
2. **Given** the marker is applied, **When** a screen reader encounters a required field, **Then** the required state is announced via the accessible label.
3. **Given** forms previously using ad-hoc markers, **When** the feature is delivered, **Then** all of them use the single shared marker treatment (no remaining one-off implementations).

---

### User Story 7 - HTML tooltips on applicant fields (Priority: P2)

Applicant-facing form fields need inline help. Each such field must show an info icon beside it; hovering the icon reveals a tooltip whose content supports HTML (formatting, lists, emphasis), not plain text only. The tooltip mechanism is scaffolded in the codebase but currently inert (no copy, renders nothing).

**Why this priority**: Directly improves the applicant experience and reduces support load; completes a previously deferred requirement (spec 021 FR-020 / OQ-8). P2 because it is additive and not on the critical decision path.

**Independent Test**: On each applicant-facing form, confirm every field has an info icon, hovering it shows a tooltip, and a tooltip containing HTML markup renders as formatted content rather than escaped text.

**Acceptance Scenarios**:

1. **Given** an applicant-facing form field, **When** the form renders, **Then** an info icon appears beside the field label.
2. **Given** the info icon, **When** the user hovers (mouse-over) the icon, **Then** a tooltip appears; when the pointer leaves, it dismisses.
3. **Given** tooltip copy that contains HTML (e.g. bold text or a bulleted list), **When** the tooltip is shown, **Then** the HTML renders as formatted content, not as literal escaped markup.
4. **Given** the es-CR culture, **When** any tooltip is shown, **Then** its copy is in Spanish (Costa Rica), consistent with the rest of the UI.
5. **Given** a field with no authored copy, **When** the form renders, **Then** no empty/broken tooltip icon is shown for that field.

---

### User Story 8 - Restructure the left sidebar into grouped sections (Priority: P2)

The left sidebar is a flat list. It must be reorganized into three labeled groups — **Inicio**, **Administración**, and **Proceso** — without removing any existing destination. The example grouping provided by the stakeholder was illustrative and did not enumerate every current item; this restructure is a **regrouping with zero removals**: every item present in the current sidebar must still be reachable in the new layout, just placed under a group. Role-gating for every item is preserved exactly.

**Why this priority**: Improves navigation and scales with the growing admin/process surface area; purely structural; no behavior change to destinations.

**Independent Test**: Compare the full set of links/destinations in the current sidebar against the new sidebar for each role (admin, reviewer, applicant, supplier-admin); confirm the new sidebar contains every destination the old one did, grouped under the correct header, with identical role visibility.

**Target grouping** (illustrative example from the stakeholder, to be completed with all current items):
- **Inicio**
- **Administración**: Empresas proveedoras, Plantillas base, Reportes (admin-wide), Moneda, Tipos de cambio, Usuarios, Configuración del sistema
- **Proceso** (headed by the Procesos link): Grupos, Starters, Plantillas de impacto, Cotizaciones pendientes

"Starters" denotes the applicants/companies who start applications under a Process; it surfaces the existing applications listing as a first-class navigation item, filterable by Process. (Process-scoped Reportes/Plantillas — originally floated as duplicates of the admin-wide surfaces — are deferred to a future spec, since no process-scoped routes exist yet; the admin-wide Reportes and Plantillas base remain under Administración.)

**Acceptance Scenarios**:

1. **Given** the current sidebar for a given role, **When** the new grouped sidebar renders for that same role, **Then** every destination reachable before is reachable after — no item is dropped.
2. **Given** an admin user, **When** they view the sidebar, **Then** they see the Inicio, Administración, and Proceso groups with their items under the correct headers.
3. **Given** a reviewer or applicant, **When** they view the sidebar, **Then** the items they were previously entitled to (e.g. Mis solicitudes, Cola de revisión, Generar convenio, Bandeja de firmas) remain visible and role-gating is unchanged.
4. **Given** the supplier-admin-only variant, **When** they view the sidebar, **Then** their narrowed entry set is preserved.
5. **Given** the Proceso group, **When** an admin opens "Starters", **Then** they reach the applications listing, scoped/filterable by Process.
6. **Given** the deferral of process-scoped Reportes/Plantillas, **When** an admin views the sidebar, **Then** admin-wide Reportes and Plantillas base appear once under Administración (no duplicate process-scoped entries) and the Proceso group shows Procesos, Grupos, Starters, Plantillas de impacto, and Cotizaciones pendientes.

### Edge Cases

- **US1**: Generator account deleted after generation → stable fallback label, never a GUID, never an error.
- **US2**: Confirmation dismissed, or the user navigates away mid-confirm → no state change. Double-submit (rapid re-click) must not bypass the confirmation or double-execute.
- **US3**: Applicant with missing optional fields (no phone, no group, no code yet) → neutral placeholders, not blanks/errors.
- **US4**: A line with zero quotations, or a line still pending (neither approved nor rejected) → rendered consistently with a clear status; pending lines are not misrepresented as approved or rejected. A line with multiple quotations in mixed currencies → each amount shows its own currency/CRC note.
- **US5**: Two reviewers editing the same applicant's code → last write wins; no crash. Code left blank/cleared → field returns to unset and displays the neutral placeholder. Very long input → bounded to the existing field length.
- **US6**: A form that is entirely optional fields → no markers shown. A conditionally-required field → marker reflects its required state in context.
- **US7**: Tooltip copy is authored (curated), not applicant-supplied; HTML rendering applies only to curated tooltip strings, so it introduces no user-content injection surface.
- **US8**: A role that sees only a subset of items → empty groups are not rendered as bare headers; a group with no visible items for that role is omitted.

## Requirements *(mandatory)*

### Functional Requirements

**US1 — Generator name**
- **FR-001**: The funding-agreement page MUST display the generating user's human-readable display name in the "generated by" attribution, never a raw user identifier.
- **FR-002**: Display-name resolution MUST follow the order full name → email → stable fallback, and MUST degrade gracefully when the generating account no longer exists.

**US2 — Confirm signed-convenio actions**
- **FR-003**: The "Aprobar" (execute) and "Rechazar" actions on the signed-upload section MUST require an explicit confirmation step before committing.
- **FR-004**: Each confirmation MUST state the consequence of the action in es-CR ("Esto ejecuta el convenio." / "Esto rechaza la carga; el solicitante podrá enviar otra.").
- **FR-005**: Dismissing a confirmation MUST result in no state change. Confirming MUST perform the action.
- **FR-006**: The reject path MUST continue to require and enforce its mandatory rejection comment.

**US3 — Richer applicant detail**
- **FR-007**: The funding-agreement page MUST show, for the applicant: company name, representative name, legal identification value and type, email, phone, the reviewer-assigned applicant code (FR-013), the applicant's group, and the submission date.
- **FR-008**: Missing optional applicant fields MUST render a neutral placeholder, not a blank or error.
- **FR-009**: This expansion MUST be screen-only; the generated funding-agreement PDF document body MUST remain unchanged from spec 018.

**US4 — Consistent decision summary**
- **FR-010**: The same detailed per-line decision summary MUST render on all five interaction screens (reviewer item review, applicant accept/reject, reviewer generate-agreement, applicant signing, reviewer signed-document review).
- **FR-011**: Each line in the summary MUST show: line code, product/type, category, technical specifications, approved supplier name, amount (with currency and CRC conversion note when non-CRC), and decision status — for both approved and rejected lines.
- **FR-012**: A rejected line MUST additionally show its rejection reason and the full set of suppliers quoted for that line with their amounts. A pending line MUST show its pending status without being presented as approved or rejected.

**US5 — Reviewer-assigned applicant code**
- **FR-013**: Reviewers and admins MUST be able to assign and edit a per-applicant code from the first review screen; the value MUST persist against the applicant (per-user).
- **FR-014**: The applicant code MUST be read-only on the applicant's own profile (no edit control there).
- **FR-015**: The applicant code MUST be distinct from and independent of the applicant's legal identification (no cross-validation).

**US6 — Required-field markers**
- **FR-016**: Every required field on every form (applicant, admin, reviewer) MUST display a single consistent visual marker (red asterisk) with an accessible label ("campo obligatorio"); optional fields MUST show no marker.
- **FR-017**: Required-field marking MUST be provided by one shared mechanism; ad-hoc per-view markers MUST be replaced by it.

**US7 — HTML tooltips on applicant fields**
- **FR-018**: Each applicant-facing form field MUST show an info icon beside it that reveals a tooltip on mouse-over and dismisses on mouse-out.
- **FR-019**: Tooltip content MUST support HTML rendering (formatted content), not plain text only.
- **FR-020**: Tooltip copy MUST be authored in es-CR for all applicant-facing fields; a field with no authored copy MUST NOT render an empty/broken tooltip affordance.

**US8 — Sidebar restructure**
- **FR-021**: The sidebar MUST be organized into three labeled groups: Inicio, Administración, and Proceso.
- **FR-022**: Every destination present in the current sidebar MUST remain reachable in the new grouped sidebar — the restructure removes nothing.
- **FR-023**: Role-gating (including the applicant/reviewer top-level items and the supplier-admin-only variant) MUST be preserved exactly.
- **FR-024**: "Starters" MUST surface the existing applications listing as a navigation item, scoped/filterable by Process. Admin-wide "Reportes" and "Plantillas base" remain under Administración. Process-scoped Reportes/Plantillas surfaces are explicitly **deferred to a future spec** (no such routes exist today); the Proceso group comprises Procesos, Grupos, Starters, Plantillas de impacto, and Cotizaciones pendientes.
- **FR-025**: A group with no items visible to the current role MUST NOT render as a bare header.

**Cross-cutting**
- **FR-026**: All new and changed UI copy MUST be es-CR; no English-only copy.
- **FR-027**: No database schema change is introduced by any requirement in this feature.

### Key Entities *(no new entities; existing ones referenced)*

- **Applicant**: The applying company/representative. Carries the legal identification (value + type) and the per-user reviewer-assigned code (an existing but previously unwritable field). Belongs to a Group.
- **Application**: A submission containing the items/lines. Reaches a Process via its Group.
- **Item / Line**: A requested resource carrying product/type, category, technical specifications, line code, decision status, and (when approved) a selected supplier.
- **Quotation**: A supplier's quote for a line — supplier, price, currency, CRC-converted amount, validity.
- **Funding Agreement**: The generated document and its lifecycle (generated → signed → executed/rejected), carrying the generating user reference.
- **Group / Process**: Grouping structures; the Process is reached from a Group, and underpins the Proceso navigation group and the Process-scoped surfaces.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: No raw user identifier (GUID) appears anywhere on the funding-agreement page; the generator is identified by name (or email fallback) in 100% of cases.
- **SC-002**: Executing or rejecting a signed convenio is impossible without passing an explicit confirmation step; 0% of these actions commit on a single unconfirmed click.
- **SC-003**: At all five interaction stages, the per-line decision summary presents the identical set of fields (including technical specifications) for both approved and rejected lines — verified by walking one application through every stage.
- **SC-004**: A reviewer can set an applicant code from the first review screen and it appears (read-only) on that applicant's profile and on the funding-agreement page.
- **SC-005**: 100% of required fields across all forms display the standard marker with its accessible label; no form retains an ad-hoc marker implementation.
- **SC-006**: 100% of applicant-facing fields present an info-icon tooltip that opens on hover and renders authored HTML copy correctly.
- **SC-007**: The new sidebar contains every destination the old sidebar contained for each role, grouped under Inicio/Administración/Proceso, with identical role visibility — verified by a per-role before/after destination comparison.
- **SC-008**: The full E2E suite passes (the team delivery bar: a feature is not delivered until the full E2E suite has been personally executed and is green).
- **SC-009**: The generated funding-agreement PDF document body is unchanged in content scope relative to spec 018 (no decision-summary expansion leaks into the PDF).

## Assumptions

- The display-name resolution capability used for commission members on the same page is reused for US1 (no new lookup mechanism needed).
- The confirm-dialog infrastructure from spec 024 satisfies US2 without new dependencies.
- The reviewer-assigned code reuses the existing per-user code field; "per applicant" means per applicant user account, shared across that applicant's applications (US5). No schema change.
- The tooltip mechanism reuses the existing scaffold (hint attribute + tooltip partial); the work is wiring it to render an icon-triggered, HTML-capable tooltip and authoring first-pass es-CR copy, which the stakeholder will later refine.
- Tooltips and other interactive widgets are driven without relying on a global Bootstrap JS object (the vendored Tabler build does not expose one); existing project patterns are followed.
- "Starters" reuses the existing applications listing surface rather than introducing a new data model; the Process filter is derived via the Group→Process relationship.
- The user profile (view/edit/change-password) is already shipped and functional and is out of scope unless a specific gap is identified.
- es-CR is the default culture and all assets are vendored (no CDN).

## Dependencies

- **Spec 024** (toast/confirm dialogs) — US2 confirmation step.
- **Spec 018** (PDF template) — US3/US4 boundary: PDF document body unchanged.
- **Spec 021** (Process/Group, the per-user code field, the hint/tooltip scaffold, FR-020) — US5, US7, US8.
- **Spec 026** (identification value object) — US3 legal-ID display formatting.
- **Spec 016** (user groups) — US3 group display and US8 Process linkage.
- Existing display-name resolution service — US1.

## Out of Scope

- Changing the funding-agreement **PDF document content** (spec 018 minimalism preserved; all decision-summary expansion is on-screen only).
- The user **profile** view/edit/change-password feature (already shipped and functional).
- **Check-digit** validation of legal IDs (spec 026 governs identification format).
- Any **database schema change**.
