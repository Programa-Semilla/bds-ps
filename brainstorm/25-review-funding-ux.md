# Brainstorm: Review & Funding-Agreement UX Refinements

**Date:** 2026-05-26
**Status:** spec-created
**Spec:** specs/027-review-funding-ux/

## Problem Framing

A stakeholder walkthrough of the funding-agreement flow produced eight refinements spanning a visible bug, two consequential-action guards, a cross-cutting data-consistency gap, a dangling field with no write surface, and three UX-consistency asks (required markers, tooltips, sidebar). The connective tissue: submitted-item decision data should be ample and identical in shape at every reviewer/applicant touchpoint, reviewers should have the controls they expect, and forms should explain themselves.

Current-state mapping (four parallel Explore agents) established what already exists vs. what is scaffolded-but-inert vs. missing — which reframed several asks from "build" to "wire" or "fix":
- The "generated by GUID" is a two-line bug (`GeneratedByDisplayName` fed the raw userId); the display-name resolver already exists.
- `CodigoPersonal` exists as a column + read-only profile display but has **no write surface anywhere** — a dangling field, not a working feature.
- The tooltip scaffold (`[Hint]` + `_HintTooltip.cshtml`) is present but intentionally renders nothing (copy deferred as spec-021 OQ-8).
- The user profile (view/edit/change-password) is already shipped — out of scope.
- The applications "listing" lives as a Reports sub-tab; `AdminApplicationsController` is only a soft-delete endpoint.

## Approaches Considered

### Packaging: one spec vs split vs per-thread
- **A — One consolidated spec** (chosen): matches the 021-feedback-session pattern; one review/plan/implement cycle.
- B — Split heavy (decision-summary) from polish bundle.
- C — One spec per thread (023/024/025/026 cadence). Most overhead.

### Thread 3 — "ample detail": PDF vs screens
- Initial framing assumed PDF expansion (the stakeholder's wording mentioned "el PDF"). **Clarified:** the expansion is on the **screens** where reviewer/applicant interact, at all five stages; the PDF document body stays minimal (spec 018). Resolves a latent conflict with spec 018.

### Reviewer identifier: reuse vs new field
- **Reuse `CodigoPersonal`** (chosen): wire a write surface on the first review screen; per-user; no schema change. Alternatives (new per-application or per-applicant column) rejected to avoid migration and a second redundant concept.

### Required markers / tooltips scope
- Required markers: **every form** (admin/reviewer included), not just applicant.
- Tooltips: **Claude drafts es-CR HTML copy**, stakeholder refines (vs ship-empty or wait-for-strings).

### Menu
- The shared tree was illustrative; restructure is a **zero-removal regroup** — every current item survives, grouped under Inicio / Administración / Proceso, role-gating preserved. "Starters" = applicants/companies under a Process, surfacing the existing applications listing filtered by Process.

## Decision

One consolidated spec — `specs/027-review-funding-ux/` — with eight independently testable user stories (P1: US1 generator name, US2 confirm execute/reject, US4 decision summary; P2: US3 applicant detail, US5 reviewer code, US6 required markers, US7 tooltips, US8 sidebar). No schema change. PDF document body unchanged. es-CR throughout. Spec review: SOUND (no critical/important issues).
